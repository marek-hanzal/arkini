# Arkini 0.5.0

Arkini 0.5.0 turns the application into both a more complete game and a practical game-authoring environment. Players get clearer production controls, finite self-consuming resources, authorable navigation between spaces, more reliable item delivery, and stronger Board, Toolbar, Inventory, package, save, and desktop lifecycles. Game authors get a complete integrated Editor with playable scenarios, dependency analysis, portable source files, reproducible project history, canonical builds, signing, and AI-assisted authoring.

This is a pre-stable release with a fresh external-data contract. Read the migration notes before relying on projects, saves, scenarios, or Arkpacks created by earlier development builds.

## For players

### Production and queues

- Production queues follow one consistent FIFO lifecycle. A queued request may wait for missing materials, the engine schedules eligible materials through physical delivery, and the job starts only after those materials have actually reached the input.
- `Ctrl + left click` on a line owner fills the remaining capacity of its default production queue in one action. A normal left click keeps the ordinary primary action.
- Queue filling is atomic: the engine admits the largest valid prefix without partially corrupting the queue when capacity or another gameplay condition is reached.
- Material delivery is owned entirely by the game engine and Tick. Production no longer depends on a Pixi animation or screen being mounted to complete a transfer.
- Items with active jobs cannot accidentally be consumed as line inputs. Moving an idle line owner into an input also clears or reconciles its queues, default line, buffered inputs, and in-flight deliveries as one canonical transition.

### Finite resource production

- Deposits can expose their own production lines and spend their own finite charges.
- Well I demonstrates this mechanic: it produces water through its own line and runs dry after 30 draws.
- Deposit lines use the same queues, jobs, rules, outputs, and deterministic completion lifecycle as other production owners.

### Space actions and navigation

- Authored Space items can act as doors, portals, elevators, or other navigation controls between game spaces from the Board, Toolbar, or Inventory. One-way routes are supported.
- Availability can depend on ordinary rules and explicit Simple or Board Deposit inputs. Only authored input costs consume items or charges; merely having charges does not spend one.
- Activation commits costs, stack changes, depletion, outputs, events, and the destination switch as one engine-owned transition. A failed action leaves the source state unchanged.
- Source-space effects finish before navigation is presented, and every space retains its own items, jobs, queues, and runtime state when the player moves elsewhere and returns.

### Board, Inventory, and Item Detail

- Board and Toolbar interactions are consistent: left click executes the primary action, `Ctrl + left click` fills the default queue, `Shift + left click` splits a Board stack, and right click opens Item Detail without triggering another action.
- In Inventory, left click releases the selected item and right click opens Item Detail.
- Item Detail focuses more clearly on current work, input progress, queues, outputs, and the reasons why a line or output is currently unavailable.
- Authored rule hints can explain active line and output restrictions directly to the player instead of exposing only a generic disabled state.
- Drag and drop, stack transfers, swaps, directional merges, and material delivery were hardened around stale identities, ownership changes, partial remainders, and interrupted animations.
- Board, Toolbar, and Inventory preserve tile identity and motion more consistently across transfers and route transitions.

### Visual presentation

- Items can use a composed two-layer default appearance while retaining separate progress-state artwork.
- Production, queue, stack, delivery, and motion presentation has been refined without moving gameplay truth into the renderer.
- Settings now starts at the standard viewport padding instead of reserving a large logo area, while preserving the launcher artwork as an uninterrupted route-transition layer.
- Common, Game, and Dev settings share a stable full-height panel while only the selected section content crossfades and the active tab switches.

### Desktop behavior

- Window modes provide explicit Default, Bordered, and Fullscreen choices, with `F11`, `Alt + Enter`, native fullscreen, maximize, and unmaximize changes synchronized back to the saved setting.
- Window-mode changes complete only after the operating system confirms the requested transition and the preference is saved.
- Superseded requests, interrupted callers, native timeouts, retries, and application close now settle predictably instead of leaving Settings in an unconfirmed state.
- Cheat tools are presented as an optional player feature under Game settings, while command-line and diagnostic controls live under Dev settings.
- The packaged CLI installer can explicitly replace a conflicting command file, and can install, repair, replace, or remove generated Bash, Fish, and Zsh completion independently.
- Pending UI actions keep their labels and icons stable while the owning control is disabled, avoiding layout shifts during fast operations.

## For game authors

### Complete integrated Editor

- Create a fresh project, import a validated Arkpack through the native file picker, or open a current portable Editor project folder directly in place.
- Author the complete game configuration: metadata, Board and Inventory dimensions, Toolbar layout, resources, initial state, items, assets, charges, merge rules, production lines, inputs, outputs, rolls, placement, conditions, and line rules.
- Create, edit, rename, convert, and delete items through routed forms with local validation and protected unsaved drafts.
- Item deletion shows every reference that blocks a safe delete. Explicit force deletion removes the item and the previewed dependent structures in one revision-checked project write.
- Asset deletion is similarly guarded by usage analysis.
- Import PNG files directly or copy selected assets from another Arkpack without adopting its game configuration.
- Export the complete current portable project, including assets, notes, scenarios, and version history. The exported folder can be opened directly by the Editor.

### Canonical project format

- The portable project directory is the single source accepted by both the Editor and `arkini-cli game pack`; there is no separate legacy or simplified authoring path.
- `project.json` owns the Arkini writer version and current project revision.
- `game.json` owns package identity through `meta.id`, project-owned gameplay compatibility through `version`, and all non-item game configuration.
- Every `items/<type>/<uid>.json` file contains one explicit item document. Its path owns the item type and immutable UID, while the item owns its human-readable gameplay ID.
- The generated root `schema.json` and explicit per-file `$schema` references make the complete project directly inspectable and validateable by external JSON tooling.
- Assets and resources are explicit PNG files; notes, scenarios, versions, objects, locks, and build output are Editor sidecars and never become game content accidentally.

### Build, sign, save, and install

- Build validates one exact saved project revision and publishes its canonical artifact below the ignored `<project>/build/` directory.
- Build filenames are derived from the project ID through one collision-safe, dot-safe encoder and always publish one self-contained `.arkpack`.
- A changed project makes the previous build visibly stale and must be built again; stale source cannot be silently published as current output.
- Local and Editor builds are Community. Tagged release automation may embed keyless Sigstore proof without any stored signing key or Editor key field.
- `Save as…` publishes the one `.arkpack` through one native destination flow. The primary catalog action is `Install` for a new package and `Update` when that package ID is already installed.
- Same-major updates proceed directly. A gameplay- or project-major upgrade or downgrade requires explicit confirmation, is revalidated immediately before publication, and never silently deletes the existing save.
- Arkpack replacement is atomic and rollback-safe; failed publication restores the previous complete file.
- Filesystem locks serialize CLI, Editor, catalog, install, removal, and recovery operations across processes.

### New authoring capabilities

- Every item has a stable internal `uid`. The UID survives authoring-ID renames, project export and import, and Arkpack rebuilds.
- Initial Board and Toolbar entries can define an exact stack quantity at an exact position.
- Initial Inventory entries can define both quantity and an optional exact slot.
- Deposits may own one or more production lines and use exact self-targeted charge inputs, enabling finite resource nodes such as wells, mines, or harvestable deposits.
- Space items define an authored target space plus optional rules, Simple or Board Deposit costs, charges, depletion, outputs, artwork, merge behavior, and limits. They can be created and edited through both the Editor UI and MCP.
- The live Editor Board can switch to any zero-based space directly, making multi-space projects testable without constructing a navigation path first.
- Added `RuntimeAdjust`, a conditional line rule that adds or subtracts a fixed number of milliseconds after active runtime multipliers are applied.
- Line and selected-output rules can include player-facing hints shown when the rule affects current gameplay.
- Item assets support a one- or two-layer default composition plus optional progress-state sources.
- Project diagnostics point back to actionable authoring entities and source locations more consistently.

### Flow and Estimate

- Flow provides a global visual map of item acquisition and consumption relationships.
- Navigate in either input or output direction, change relationship depth, focus a root item, and follow producers and operations directly to their owning Editor sections.
- Estimate performs static authored-graph analysis for any item and quantity.
- It reports optimistic parallel critical-path duration, expected random-output economics, required materials, owners, infrastructure, deposits, and positive enable prerequisites.
- The global Estimate view supports search, incomplete-only filtering, fastest and slowest ordering, and aggregate-demand ordering to reveal overused items or disconnected ballast.
- Flow ranking and Estimate strongly connected components use deterministic graph traversal, including stable results for cycles regardless of authored insertion order.
- Estimate is intentionally an authoring reference rather than a runtime simulation: it does not pretend to model placement, finite capacity, charges, renewal, or every live rule interaction.

### Playable Editor Board and scenarios

- Run the real game directly inside the Editor using the same engine, Board, Toolbar, Inventory, Item Detail, audio, Pixi presentation, and commands as the packaged game.
- The live Editor Board is disposable and never autosaves into the authored project.
- Explicitly save named Board scenarios for reproducible testing, restore them later, or delete them when no longer useful.
- Scenarios carry project revision and gameplay-version provenance. Compatible project edits preserve them; a major gameplay-version change removes them before publishing the changed project.
- Saved scenarios are portable with the project and included in project version snapshots, but never included in the built Arkpack.

### Notes and project history

- Add portable project notes without including them in the game build, project revision fingerprint, or version snapshots.
- Create complete project versions containing configuration, items, assets, resources, and Board scenarios.
- Inspect working-copy status, browse version history, compare any two versions or the current saved working copy, and assign optional human-readable tags.
- Restore a compatible version directly in the open Editor without restarting the application. Restore is an explicit destructive action and discards the current saved state and unsaved drafts.
- Version history validates snapshot metadata, parent links, object hashes, graph structure, and every referenced object before trusting a restore or comparison.

### Safe project export

- Source export creates a new uniquely named `<project-id>-json-<suffix>` child inside the selected directory instead of replacing an existing folder. Multiple exports can safely coexist.
- Only the portable project allowlist is copied. Git metadata, Editor locks, build output, temporary files, and unrelated source-directory content are excluded.
- The completed child is reopened through the production project, sidecar, and version-history readers before success is reported. Failure or interruption removes only that new child and never modifies the chosen parent or source project.

### Editor navigation and workflow

- Added dedicated workspaces for Project, Notes, Items, Estimate, Assets, ChatGPT, MCP, Flow, Board, Versions, and Build.
- Added collision-safe global workspace shortcuts while preserving local Board and form controls.
- Workspace shortcuts are disabled while typing, while a modal or unsaved-changes prompt is active, and during Editor exit.
- History-aware back navigation preserves list filters and search where appropriate and provides deterministic fallbacks for deep links.
- Version restores, project refreshes, imports, and other major lifecycle actions update the mounted Editor in place.

## AI-assisted authoring

### ChatGPT workspace

- ChatGPT can run inside a dedicated, sandboxed Editor workspace while Arkini retains its own navigation and project ownership.
- The ChatGPT session is isolated from Arkini IPC and local project access.
- A visible ChatGPT workspace may download one bounded PNG. Arkini validates the bytes and requires explicit confirmation before inserting a new asset or replacing an existing one.

### Editor MCP

- Start an open local MCP endpoint for tools on the same machine or an OAuth-protected remote endpoint exposed through ngrok.
- MCP always targets only the project currently open in the Editor and remains off until explicitly started.
- Read project summaries, project configuration, validation results, item collections, complete item configuration, input and output relationships, individual estimates, and the global Estimate index.
- Create and edit every supported item type, update non-item project configuration, and rename item IDs together with their exact references.
- Preview item-deletion impact before performing a safe or forced revision-checked deletion.
- Read version status and history, compare versions, create snapshots, tag them, and explicitly restore compatible versions.
- MCP mutations use the same canonical saved project and revision checks as the Editor UI; they do not maintain a second copy of the game.
- Remote endpoint health checks use bounded retries and cancel timed-out or abandoned requests cleanly.
- Ngrok reconnect scheduling has one scoped lifecycle: repeated disconnects replace the old countdown, a successful connection cancels stale reconnect work, and explicit shutdown interrupts reconnect before closing the native listener.
- Persisted OAuth clients, authorization codes, access tokens, and refresh tokens are validated strictly; corrupt state resets instead of entering the live identity indexes.

## Arkpacks, saves, and distribution

### Arkpack identity and provenance

- A package has one identity: the signed game configuration `meta.id`. It is not duplicated in the Arkpack payload, manifest, catalog, or filename metadata.
- The application scans bundled and user package folders directly instead of relying on generated catalog metadata.
- A structurally valid user package may override a bundled package with the same ID. Removing the user override reveals the bundled package again without deleting its save.
- Official provenance comes only from offline verification of the embedded Sigstore proof over the immutable inner gameplay payload, exact full build version, issuer, repository, and workflow identity. Every failed proof becomes playable Community content.
- Package loading independently revalidates filename identity, configuration identity, resources, compatibility, provenance, and gameplay content hash before starting a game.
- Runtime resources are the explicitly supported PNG payload type; Arkpacks remain data-only and never contain executable JavaScript or HTML.

### Persisted data and compatibility

- Gameplay saves use the compact versioned envelope `{ version, arkini, state }` and remain separate from package files.
- Save directories encode package identities safely instead of restricting valid authored IDs to filesystem-friendly names.
- Arkini writer versions retain full `major.minor.patch` provenance, but only a mismatching major is a version-level reason to reject structurally current Arkpacks, saves, Editor projects, scenarios, or version history. Minor and patch versions never select another parser, migration, fallback, or conditional data path.
- Project-owned gameplay compatibility is separate: a save or Board scenario is version-compatible when its gameplay major matches, regardless of minor ordering. A gameplay-major mismatch is rejected without clearing or overwriting the persisted data.
- Removing or replacing an imported package does not delete its save.
- Invalid package data never exposes save deletion. Save recovery is offered only after a verified package fails specifically during save decoding or runtime hydration.
- Save writes remain atomic: a failed replacement leaves the previous successful save intact.

### CLI and desktop delivery

- The macOS application ships an installable `arkini-cli` for project schema generation, validation, canonical packing, and offline provenance verification. Signing is release-automation-only.
- The Editor, CLI, repository build, and packaged official Arkini all use the same portable project compiler and standard `game pack` path.
- Repository versioning updates application metadata, the lockfile, and the official project's Arkini writer version as one rollback-safe operation.
- Hosted repository validation runs independently on Linux, macOS, and Windows development branches, while `main` remains an intentional release-only escape hatch.
- Release tags produce separate unsigned macOS Apple Silicon DMG and ZIP, Windows x64 installer and ZIP, and Linux x64 and arm64 AppImage applications with self-contained target checksums. Every application embeds the exact same once-signed Official Arkpack bytes; development prereleases also publish that file standalone.

## Reliability

- External project, export, build, Arkpack proof, save, scenario, version-history, JSON Schema, and OAuth data now have explicit ownership and validation contracts.
- Shared recoverable filesystem writes serialize competing processes, validate paths and ownership, sync staged file contents, recover interrupted replacements, and preserve the previous committed state on failure. External project operations modify only exact Arkini-owned paths, leaving Git metadata and unrelated files untouched.

## Authoring and migration notes

- Arkini 0.5.0 remains pre-stable. Structurally current persisted data with a matching Arkini major is admitted regardless of its writer minor or patch version, but obsolete development shapes may still fail strict current-shape validation.
- No automatic migration, legacy reader, or conditional compatibility path is provided for unsupported pre-0.5.0 Editor projects, Arkpacks, saves, scenarios, version history, or other persisted Arkini data.
- The current Editor accepts only the current portable project format rooted by `project.json`; legacy arbitrary-fragment or simple-config layouts and previous IndexedDB or SQLite Editor storage are not imported automatically.
- Every authored item requires a globally unique stable `uid` in addition to its human-readable `id`.
- Item categories and tags were removed from the game contract.
- Tag-based selectors were removed; inputs, queries, merge rules, and other relationships use explicit item references.
- Quantity authoring is normalized to inclusive `{ min, max }` bounds.
- Obsolete authored cheat item kinds were removed. Cheat mode and Instant gameplay are persisted runtime switches, while destructive save reset remains an explicit application lifecycle action.
- Older source projects must be recreated or deliberately converted to the current portable schema and packed again.
- The durable no-data-break guarantee begins only after the product owner explicitly declares the first stable baseline and does not apply retroactively to obsolete development shapes. Major-only reader admission already applies to every structurally current persisted envelope.
