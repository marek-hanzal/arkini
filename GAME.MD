# Serakki gameplay contract

This document owns implemented gameplay meaning. [`CONFIG.md`](CONFIG.md) owns authoring syntax; [`ARCHITECTURE.md`](ARCHITECTURE.md) owns execution and lifecycle; source and focused tests prove the current implementation.

## World and item locations

Serakki runs multiple isolated Board spaces. A Board cell is `space + x + y`; equal coordinates in different spaces never interact. `currentSpace` selects presentation. All spaces keep simulating.

Each Board cell holds one item identity or one delivery-origin lease. Birth, outcome, return and merge replacement use the same occupancy rules; ordinary placement into an occupied destination rejects the operation atomically. Explicit forced removal may discard capacity overflow within its atomic transition. Board interaction has no layer selection or hidden occupant.

A new game expands each authored space-to-template assignment against one evolving candidate Runtime. The template defines that space's dimensions and cells; reusing one template creates independent item identities in every assigned space. Unmapped spaces are empty and use the project fallback dimensions. Space and coordinates are exact; every cell uses canonical placement, and `currentSpace` and the complete initial item state commit atomically or not at all. Board dimensions always come from the loaded Serapack: the assigned template, or project fallback for an unmapped space. Saves store gameplay state, never board dimensions; loading restores existing items without reapplying template placements or comparing saved coordinates against current board dimensions. Version compatibility governs content updates. Bounds are enforced when placing or moving items, not by revalidating all existing positions after an update.

Applying a template replaces exactly one space atomically. All its physical items, deliveries, nested input buffers, consumed/reserved material, jobs, queued work, selected lines and item schedules are discarded without refunds or completion/expiry outputs. Fresh item identities are created from the template. Rooms owned by discarded identities are recursively destroyed too. Other surviving spaces and global switches remain unchanged; an already admitted delivery whose producer travelled into the reset space returns to its original leased cell. New-game start uses this same operation for every initial assignment. Runtime and saves retain only each space’s active template UID; its dimensions remain Serapack-owned. A Template outcome invokes this operation in its origin space, even while another space is viewed. Outcomes retain authored order: earlier item outputs are discarded by a later reset; later item outputs settle on the replacement board. Captured cleanup obligations for identities destroyed by the reset are dropped, never resurrected.

Board-relative distance, placement, merge and outcome remain in their origin space. Unit payers always belong to their producer’s home space. Material Autofill always stays in its producer’s home space, independently of the currently viewed space. Items have no authored storage scope.

Queries have one `distance`: `self` matches the origin, `close` distance one, `near-close` one or two, `near` exactly two, `far` every positive distance in the origin's Board space. Query callers supply a physical Board origin; all queries stay in that space. Internal input, job, reserved and delivery locations are never direct query candidates.

Every runtime item represents one instance. Each start entry creates one identity in its exact cell; authored input and outcome quantities count separate instances. Units, schedules and production ownership stay attached to that identity.

## Lines, intent, and delivery

An authored line has one immutable project-unique `uid`. Its title is presentation only. Editor creation and copying assign fresh UIDs; editing and reordering retain them. Runtime production references the line UID together with the owning runtime Item instance.

Item production lines share one lifecycle. Each item owns zero or more `lines`; without lines it is passive. Production uses `maxQueueSize` (default `1`). A default line selects the click action; it does not schedule work automatically. Input filling is passive and never starts work. Each material input stores at most its authored `quantity.max`; there is no extra input capacity. Enqueue is the player-facing execution command: it appends explicit intent after validating the owner, line, rules, non-material requirements, units and queue capacity. Missing concrete material may wait.

A queued request is not a job. It owns no time, material, unit, or reservation. The persisted global queue retains accepted intent order. Each queue pass traverses that array in order against the latest Runtime draft and selects the earliest actionable request for each idle Board owner. A request makes progress by a successful start settlement or by scheduling useful canonical Autofill delivery while its rules, non-material requirements, units hold. A start may settle an internally held material's terminal Template outcome and remove its new Job before publication; that settlement still counts as progress for this pass. Only progress marks its owner as handled for that pass; blocked requests may be overtaken. Other owners compete for shared resources in the same global traversal order.

A blocked probe changes no Runtime state, stored inputs, units, reservations, deliveries, events or gameplay randomness. Skipping preserves the request's identity, line, relative array position and valid line-input ownership. Once actionable again, an older request wins over later requests for that owner. An already travelling delivery alone is not new progress. Active Jobs remain non-preemptive during queue dispatch; explicit forced owner removal can abort them. Each dispatch pass admits at most one progress-producing request per owner, including the separate passes after completion or item expiry within the same fixed step. Queue reads retain accepted request order without promising execution order.

The player may clear all pending requests for one owner without affecting its active job, units, consumed material, or reservations. Clearing atomically returns unused stored input roots for the removed request lines and reverses their outbound deliveries through canonical placement; if a stored root cannot be returned, nothing is cleared.

At a fixed-step boundary, queue playback may Autofill useful concrete material through canonical deliveries while retaining the request. Delivery travel is persisted engine state with fixed-step remaining duration. A successful Autofill admission emits one `line-input:autofill-started` event with the owner, line and scheduled quantity, shared by targeted clicks and queue playback. If a later outcome in the same Tick discards an admitted delivery, only surviving outbound deliveries count toward that event; none surviving means no event. No-op or rejected attempts emit nothing. The material becomes available only when Tick settles delivery into input storage. Renderer geometry/contact never admits material or starts work. Each delivery owns one item and targets one exact owner, line and material slot. Settlement rechecks the selector and capacity: the complete identity enters the slot or returns to its persisted origin.

Only after required material has settled may a later queue pass create the job and remove its request. Start re-resolves every live fact and commits input ownership, unit spending and the job atomically.

## Space outcomes

Space destinations may be an exact number, `"previous"`, or `{ type: "inventory", templateUid }`. Runtime and saves retain one optional `previousSpace`: the space last left by a successful committed navigation. A new game has no history. Only the transaction's final change from its original current space updates history; draft hops, same-space outcomes, net-zero round trips and rejected transactions leave it unchanged. Destruction clears references to deleted rooms, and a deleted original current room is never recorded as previous. A → B → A therefore leaves B as the previous space; this is not a history stack.

Previous Space outcomes resolve against committed history in the settlement snapshot, using ordinary rules and rolls. Without history they resolve to no outcome; other results settle normally and no replacement draw occurs. Receiver-owned transport resolves the same destination before moving the incoming item, without moving the player or updating history. Missing history rejects the entire transport interaction before target effects or outcomes and never falls back to swap.

Inventory is a shorter name for a Space owned by one exact live runtime item identity: the definition owner for outcomes and receiver for transport. Each owner has at most one Inventory Space per referenced template UID. Its first successful interaction allocates a free numeric address and expands that template once, with fresh item identities and the template's dimensions. Every authored numeric destination, start assignment and occupied runtime address is reserved. Spawning the owner does not create its rooms; self-referencing templates therefore remain lazy. Outcome navigation and receiver transport referencing the same template share the room regardless of which happens first; repeated outcomes with that template also share it without resetting contents. Different template UIDs create different rooms, even when their layouts are identical. Runtime and saves bind each creating template UID to its numeric Space; a later Template replacement inside that Space changes its active template, not its binding key. Creation, item movement, outcomes, binding and history commit atomically; failure leaves no room or binding behind. Movement, storage, reservation and replacement that preserve the item ID also preserve its rooms, including across save/load.

Destroying the owner immediately destroys all its Inventory Spaces, complete contents and work, recursively including Inventories owned by those contents. No interior refunds, completion or expiry outcomes run, and captured work cannot continue in the same Tick after destruction. The address is released for later allocation; old history never follows a recycled address. If the viewed Space disappears, navigation falls back to a surviving Previous Space, otherwise the configured start space. Expiry and depletion cannot create an Inventory after their owner has died; that result is skipped. Outcomes anchored in a Space already destroyed by the settlement cannot recreate it. The final destruction rules also apply when owner removal follows Inventory creation in the same operation.

Navigation is an ordinary `space` outcome. Portals use a default zero-duration production line and the same queue, input admission, rules, unit settlement and completion lifecycle as every other line. Player activation uses this ordinary line lifecycle. Item transport is authored independently as a receiver-owned Space merge.

Every successfully resolved Space outcome selects its authored space, including outcomes from automated production, merge, depletion and expiry. Authored order and existing lifecycle settlement order determine precedence: the last successful Space outcome wins. A transaction publishes only the final transition from its original space. Item outcomes remain anchored to the definition owner's captured physical origin regardless of navigation. An ordinary placement failure rolls back the whole operation, including navigation.

An otherwise eligible occupied-target drop first uses the dragged item's matching explicit merge, then the receiver's Space merge, otherwise swap; a selected merge rejection never falls through. Production inputs never accept dragged items. A successful swap emits one `item:swapped` event for both items, with their identities and original locations, instead of separate placement events. Rejected Board drops use the shared `item-drop:rejected` presentation SFX; ignored drops and cancelled gestures stay silent.

## Tick, jobs, and item lifetimes

Effect Clock is the production wall-clock source; simulation advances in canonical 100 ms fixed steps. In normal gameplay, a long elapsed interval equals the same sequence of explicit steps. Accelerated live playback instead limits each wake to one complete step and drops overdue accelerated wall-time debt under load. Session-only observation/remainder state is not persisted, and an attempted complete step is acknowledged once even when advancement fails.

Outcome conditions for each start, completion, and terminal settlement use that operation's pre-operation Runtime snapshot. Earlier lifecycle results in the same Tick are visible; partial changes within the current operation are not.

Jobs persist captured duration and remaining work time, plus an optional terminal cause when a self-depleted owner stays visible until that job settles:

```text
durationMs
remainingMs
terminalCause? (depleted)
```

Runnable jobs decrement by one step, clamped at zero; paused jobs do not. Completions settle in stable job-ID order. Work admitted during that boundary receives no retroactive time. Item Detail offers exact active-job cancellation on an interactive owner. Active-job cancellation consumes committed material without refunds or line outcome, returns reservations through ordinary placement, and preserves pending intent unless owner depletion removes the owner. Failed placement rolls the cancellation back; a stale job identity is a no-op. Material expiry and cheat-only forced owner removal also use the shared abort settlement.

Clock state belongs to the exact item identity. A finite lifetime persists `schedule.remainingDurationMs`, initialized from `clock.durationMs`. Enabled identities present at both step boundaries age by that step in every location scope. Moving an identity between scopes neither pauses nor resets its schedule. Job outcome created in the current step starts at full duration.

Exhausted items are evaluated after job completion in stable runtime-ID order, so a completion tied with lifetime expiry or Unit depletion wins. Clock lifetime and Units depletion both signal the item termination boundary. A Board owner draws one eligible `item-termination` line by weight and admits it as ordinary queued work; its completion settles output and owner removal. An item held inside a delivery, input or another job cannot start a Board Job: termination settles the selected line outcome immediately from its physical grid origin, skipping that line's inputs and runtime, and aborts the directly owning job. Other ways of removing an item discard its termination line without running it.

## Scheduled production

`Item.clock` adds periodic admission, finite lifetime, or both to an item. Interval pulses use the same line admission, Jobs, Autofill, units, delivery and outcome operations as manual production. Each pulse evaluates `clock-interval` lines against current rules, draws one enabled candidate proportionally to its generic line `weight`, and retains that exact selection in the admitted request. An empty pool, unavailable inputs or admission, or a full queue consumes the pulse without debt or another draw. A saved per-owner pulse sequence seeds selection independently of Tick grouping and hydration. Queue capacity counts active and pending work.

Optional `clock.intervalMs` is at least 100 ms; optional `clock.durationMs` is at least 100 ms and limits active lifetime. At least one must be present. Missing duration means unlimited lifetime; missing interval means a one-shot lifetime with no production pulses and no required lines. Both timers pause only while the clock's enable/disable rules deny availability, with Disable retaining veto precedence. An empty Clock selection skips admission but still evaluates rules and ages phase and lifetime normally. There is no separate player on/off state. Sub-step phase remainder prevents rounding drift. Every location scope earns schedule time. A periodic pulse outside Board advances phase but cannot admit Board-owned production; returning to Board does not create catch-up work. Speed up accelerates the whole simulation, including Clock pulses, jobs, deliveries and finite lifetimes. Admission retains its normal simulation-time cadence.

Every line has one `trigger`: `manual`, `clock-interval`, or `item-termination`. Manual lines alone can be Default, with at most one Default per item. Any number of interval or termination lines can participate in their weighted selection; `weight` is a generic line field (default 1, range 1–999). Runtime Default selection holds one line ID (`null` selects none). Clock interval selection follows authored triggers; there is no separate override list. The Editor authors Units and termination mode on Item, manual lines under Production, timer settings and rules on Clock, and both automatic triggers under Automation. Its new item-ending line option appears when Units or finite Clock lifetime is configured; existing lines remain editable if that signal is later removed. Item-ending lines are one shared pool for Clock lifetime expiry and Unit depletion. Accepted requests keep their selected line regardless of later selection changes.

Item `ui` controls player-facing presentation, never engine production command admission. `simple` (the schema default) shows item facts and, when one exists, the effective Default manual line's visible inputs and link-like job action together below the description. The control box centers visible inputs above a large link-like job action; with no visible inputs, the action remains centered in the same box. A pending-work Cancel control appears below the action. In Simple detail, the artwork progress bar shows a timed active job first, remaining Units when the authored amount exceeds one, and lifetime otherwise; transitions between those states are animated. Unit counts show the remaining number when full and a remaining/total fraction after use. Material inputs use the same delivery and withdrawal controls as the full line view; non-self Unit inputs display their required Board distance. The button is disabled when the line is unavailable or its requirements cannot be met; an authored rule hint explains a rule blocker below it. `default` shows item information followed by visible manual Lines in one scrollable detail, without tabs. A gone item retains its artwork and facts but shows no input panel, progress, production lines, or action button. Engine production commands do not branch on the item's `ui`. In both interfaces, a Board left click opens Item Detail. Shift+left click enqueues the effective Default line when admission is available, and Ctrl+left click fills that line's queue; either modifier falls back to Detail when admission is unavailable or no Default line exists. Authors disable click production by leaving no Default line. Opening a default item scrolls instantly to its Lines regardless of active or queued work. Lines show their queued count and active work separately. Clear removes only the selected line's pending requests, including while its active job runs. A separate trash control cancels the displayed active job and consumes its committed material without refunds.

Simple UI exposes material delivery and withdrawal for its effective Default manual line and a direct job action. An icon-and-label Cancel control appears while that line has pending work; it clears the line's pending requests without canceling active work. Simple UI has no general queue management or line selection controls. Default UI presents controls for visible manual lines, their queues and line selections. A line's availability tint includes its own outbound material deliveries so it remains stable during autofill, but production admission waits for physical settlement; its idle Play cue stays hidden while a request for that line is queued. Neither UI mode gives the player an item-removal command. After a committed change of the current Space or replacement of its Board by a Template, Item Detail disables its controls immediately and delays its exit animation until the Board transition has had time to settle, without returning focus to the previous Board; enqueueing a line alone leaves it open. Player production commands are admitted by the same engine rules regardless of presentation mode. Players can enqueue only manual lines; Clock interval lines are admitted only by their scheduled pulse. Manual and periodic requests share ordinary queue order and capacity; neither receives priority over previously accepted runnable work.

With item `terminationMode: "loose-kill"` (also the meaning of omission), existing production earns its step before interval pulses. An interval pulse tied to final lifetime may still attempt ordinary admission. Lifetime or Unit depletion then closes ordinary new intent. A selected termination line must pass input and admission checks and become an accepted request. An active old job may temporarily occupy the queue's last slot; one accepted termination request can wait beyond that capacity until the old job completes. Earlier accepted requests retain their queue order before termination work. The owner remains visible and occupies its Board cell through both jobs, then disappears when termination work finishes. If the owner’s own job spends its final Unit and no termination request is accepted, it discards pending requests but remains visible on its Board cell until that job completes. Completion removes the owner before placing its output, so the first drop may occupy the freed cell; depletion is signaled at completion, in the same committed transition as visual removal. If an already-running job reaches the terminal boundary for another reason and no termination request is accepted, the owner immediately leaves the Board and retains its identity and former Board origin only to complete that job and place its output. If idle and no termination request is accepted, the owner is removed immediately. Blocked placement retains completed work for retry.

With item `terminationMode: "kill-switch"`, lifetime expiry or Unit depletion cancels remaining owner jobs and queued requests after completions already earned at that boundary. One eligible `item-termination` line may then enqueue and run as an ordinary Job. Its completion removes the owner and uses forced-removal discard policy for output, reservations and unused stored inputs. Consumed inputs and spent units are not refunded; canceled jobs emit no line output. Incoming deliveries follow their ordinary return path. Without an eligible startable termination line, the owner is removed immediately under the same policy.

Forced removal places one identity per free Board cell. Each outcome creates as many separate items as fit; excess outcome is permanently discarded. Every reserved or stored input root either returns with its exact identity and passive owned state intact or is discarded together with that state. Cancellation, removal, all placements, and all loss facts form one candidate Runtime and commit together with its events. No intermediate removal or partial placement is published. Unexpected failures abort the entire transition; they never become silent capacity loss. `job:aborted` identifies the canceled job, owner, line and cause; `item:discarded` identifies the owner, canonical item, existing runtime identity when applicable, quantity, source and reason. Every such committed fact is also retained in the `game.removal` diagnostics log, independently of the bounded on-screen history.

## Material ownership

Material input requires a `query` containing the exact canonical item selector and the Autofill distance. `self`, `close`, `near-close`, `near`, and `far` search relative to the owner in its Board space. Automatic source selection and displayed availability apply this query independently for each input, while allocating each source identity to at most one input and excluding the owner and busy producers. Already admitted deliveries and buffered material remain accepted when the owner moves.

Material ownership uses one of two modes:

- `consume`: the material stays intact while stored; start discards its passive owned subtree, moves only the inaccessible root into `job` scope, and completion destroys it permanently. Conversion does not spend its Units or start a terminal line.
- `reserve`: start moves the same live instance into `reserved` scope. Completion relocates it from the owner's current Board origin. The same identity and its passive owned state return to one free cell.

Neither mode remembers a historical Board cell. Each committed root retains its material input index so live requirements remain attributable. Job-owned material is inaccessible to generic mutations. A material input closes while its line runs. Right-clicking a buffered material in Item Detail withdraws one exact item identity through ordinary existing-item placement and cancels pending requests for that owner and line in the same transition. Other stored inputs stay buffered; outbound deliveries for the canceled line return. Committed job material cannot be withdrawn. Left-clicking a material slot requests targeted Autofill toward its maximum through the same source selection and delivery pipeline used by queue playback. It fills only that slot, accounts for buffered material and incoming claims, and creates no queue intent or job. The command rechecks an interactive Board owner, open lifetime and non-running line atomically; a full slot is a no-op and a partial slot retains the withdrawal action. This applies equally to consumed and reserved material. Items with a finite lifetime may enter material input and keep aging through input storage and active work.

When committed material reaches its Clock lifetime, the engine aborts its parent job and settles the selected `item-termination` line outcome immediately, without that line's inputs or runtime. It never refunds units spent at start. The same internal-item contract applies to Unit depletion. For Board items, Clock lifetime and Unit depletion select the terminal line by weight after rule filtering and admit it as ordinary queued Job work. A loose-kill item lets existing work finish; a kill-switch cancels it. A blocked terminal outcome keeps the candidate transition uncommitted in loose-kill mode; kill-switch uses forced-removal discard policy. After a successful terminal pass, idle owners' queued requests are retried in global intent order against the resulting Runtime.

Cheat removal of an authored Board owner cancels its queued or running terminal Job and releases its stored input roots through canonical existing-item placement in the same transition. Other active or queued Jobs still prevent removal. Merge consume, remove, and replacement likewise cancel only terminal work when they remove the identity for another reason. Clock lifetime can also remove an item from an internal ownership location and derives its physical Board origin through that ownership chain. Any blocked release rolls the removal back.

## Units and completion

Units are an item capability available to every item: passive and manually operated resources use the same Item schema, and scheduled production adds Item.clock. A units input selects a Board item with a unit supply; it does not require a special item type. Only payers in the owner’s space are eligible, independently of the currently viewed space. Payers are ordered by Manhattan distance, row, column and runtime ID.

Authored `quantity` counts separate item instances; `units` is the finite supply inside one instance and can represent health, resource stock, or uses. Runtime items have no quantity field.

An item may author finite `units.amount`. Missing live `remainingUnits` means the fresh full amount. Input costs spend units from either the line owner (`self`) or the deterministic Board target of a units input (`target`). Queueing pays nothing.

Start reserves unit budget by runtime payer across the entire line, aggregates all costs per payer, and spends each payer once. Partial spending updates the same identity's remaining units. At zero, the item enters the shared terminal transition. Eligible Board items queue a selected `item-termination` line as normal Job work; internal material settles its selected outcome immediately. With loose-kill, an owner that spends its final Unit on its own job retains its Board cell through that job even without an accepted termination request. An active owner reaching the terminal boundary for another reason retains its cell only if a termination request is accepted; otherwise it becomes a non-Board job owner with its original output origin. With kill-switch, the old Job is aborted. Idle external payers with queued work are skipped when the aggregated cost would fully deplete them.

Completion removes the ready job and consumed roots in one candidate, keeps reserved roots live, then applies this order:

```text
place optional line outcome
→ relocate reserved instances
→ evaluate terminal state of a now-idle owner
→ enqueue its selected terminal Job or remove it if none is eligible
```

A non-depleted owner, its stored inputs, and pending queue remain. An accepted terminal line runs through normal Job admission, runtime, and output settlement; it removes its owner on completion. A departed owner remains the origin of its already running job and is removed after that job settles, without another disappearance event. Any unit, placement, capacity, or return failure preserves the pre-completion state for retry. One blocked owner does not prevent independent owners from advancing.

## Outcomes and randomness

Item counts have no global per-definition cap or future-outcome reservation. Authored query conditions control production availability; outcome settlement still requires enough compatible placement space.

An outcome table contains one or more alternative sets. Each set evaluates its availability rules against the definition owner's captured origin and the pinned Runtime snapshot before selection. Available sets contribute their positive relative weights; exactly one is selected. No available set emits nothing and consumes no selection or quantity randomness; one available set needs no selection randomness. Every roll in the selected set resolves in authored order: Guaranteed includes all eligible outcomes, while Chance shares one probability check across its entire outcome group. Separate Chance groups are independent. There is no nested weighted selection or repeated draw. Individual outcome rules run after set selection and chance resolution; rejected outcomes are discarded without replacing the set or rerolling.

Each roll first resolves into one complete ordered list, including concrete Item quantities, fixed or previous Space destinations, owner/template identities for Inventory, and Template identities, before any outcome in that roll is applied. Inventory allocation waits until its application, when the exact owner must still exist. One shared application boundary applies Item placement, Space navigation, and Template replacement in authored order. This boundary is per roll, not an aggregation across rolls, operations or Tick. Item outcomes own quantity and placement; Space outcomes own the destination; Template outcomes own the selected template. All three own availability rules. Existing lifecycle settlement and pinned rule snapshots remain authoritative.

Randomness derives from stable canonical identities and explicit algorithm versions, never Tick or wall time. Historical seeded results are not a compatibility promise; retry determinism and independence from Tick grouping are. Unchanged blocked start/completion/expiry retries therefore resolve the same rolls and placement order.

Each surviving merge definition owner also persists a `mergeSequence` cursor (omission means zero). The owner is the source for explicit merges and the receiver for Space merges. Every successful merge advances its owner cursor once; a rejected or interrupted transaction never advances it. Merge outcomes use the incoming cursor, so repeated successful `use` actions draw fresh results while preserving the owner identity. Save/load and same-identity target replacement preserve the cursor.

## Placement and merge

One Board placement policy serves ordinary drops, line outcomes, reserved-instance relocation and stored-input release:

```text
apply Board placement strategy
→ select empty locations
→ place one identity per cell
→ require the complete quantity
```

Initial placement uses exact authored Board cells. Runtime placement stays in the physical origin's Board space and chooses empty cells nearest-first against the evolving draft. `random` chooses a fresh Board origin for every resolved outcome item, including occupied cells. No outcome falls back to another Board space. Every existing item return preserves its identity and needs one empty cell. Ordinary placement requires enough cells for the complete outcome or return; a capacity failure rolls back the owning mutation.

Directional merge is one canonical gameplay command. The source item owns ordered rules; the first exact target selector wins and reverse matching is never inferred. One source item is consumed, used, or has a unit spent through source `spend`; one Board target is kept, removed, replaced, or has a unit spent through target `spend`; and optional Item outcome uses ordinary placement from the source owner origin. Merge outcome rules also use that source origin; each participant's terminal line keeps its own origin. Replacement retains the target identity and its cell. Replacing a finite-lifetime target discards its remaining lifetime and initializes the replacement's own canonical state. `use` preserves the source without spending units. After target effects and merge outcome, a surviving source is dropped through ordinary existing-item placement, anchored at the target's captured Board location. Its original cell becomes available to that relocation; a Template reset that removed it never resurrects it. This relocation preserves identity and emits `item:placed` with the target as origin. It rejects a source with schedule or explicit remaining-unit state, a Default selection override, or owned input, outbound delivery, job or queue state. Each `spend` spends one real unit from its participant and enters the shared terminal transition when the last unit is spent. A depleted source returns buffered inputs from its physical Board origin; a blocked return rolls the whole merge back. Source action, target effect, outcome, return, validation, and events commit together. When no explicit source rule matches, the receiving item may own one `space` action merge without a target selector. It transports the original dragged identity and its owned state to the nearest available cell in the authored space, using the destination Board's center cell (`floor(width / 2)`, `floor(height / 2)`) as the standard drop origin. The destination's active template supplies its dimensions, including a freshly initialized Inventory Space. It runs the same target effects and optional outcomes, with the receiver owning the outcome origin and random cursor. Transport itself does not navigate the player; a Space outcome still does. Transport, target effects and outcomes commit atomically; unavailable placement rejects the whole interaction. A failed explicit merge never falls back to receiver transport, and failed receiver transport never swaps. Without either matching interaction, the two items swap.

A merge replacement may transform a target with partially spent units. When the result has units, it inherits the number already spent; a result with no units discards the old supply. A finite result with no units left after that transfer is rejected atomically. Replacement still rejects targets with owned production state such as stored inputs, active jobs or queued requests.

## Audio

`game.json.music.playlist` is the only global random Music pool. Its entries are exact Music resource UIDs, each selected track is packaged, and the Game streams them through the two-slot crossfade mixer without treating other Music resources as playlist members. An empty or absent playlist produces no background Music. An optional item `music` resource UID temporarily requests its own track while its detail is open, without altering the global pool. The global track pauses with its position retained; opening another detail crossfades directly to its requested track, or returns to the paused global track when no music is requested. Closing the detail also restores that global track. Requests for the same track continue without restarting. Detail tracks begin at a fresh random position between 10–90% of their duration and crossfade to another random start after reaching the end; the global playlist retains its normal playback policy. SFX use their independent bounded voice mixer. Zero master or SFX volume skips new SFX loads and playback without queuing them for unmute. Music continues at zero gain so unmuting does not restart it. Each event retains one assigned SFX; per-cue variation is intentionally excluded. Sound-preference read failure logs a diagnostic and uses the default application mix without blocking startup or writing that fallback to storage. Items with `ui: simple` suppress the entire job audio family: queued, started, autofill started, completed, aborted, and queue cleared. These committed gameplay events remain available to other observers.

Committed gameplay SFX play only for facts rooted in the currently presented Space at that commit. Owner-based facts use the exact committed transition's previous runtime when the owner has already vanished; hidden Spaces continue simulating silently. Space navigation itself remains audible, and direct presentation SFX still follow visible player interaction.

Committed lifecycle events remain composable audio facts. Expiry and full unit depletion keep their own events. When the final visible item identity vanishes and its expiry, depletion, or authored removal outcome places no replacement, the same transaction additionally emits `item:disappeared`; configured outcome that rolls nothing or is fully discarded is not a replacement. An actually spawned lifecycle Item outcome suppresses only this additional event. A Space outcome is never an item replacement. Ordinary line outcome and released stored inputs are not lifecycle replacements. Merge source consumption and internal consumed production material do not emit disappearance because they are inputs to another surviving or replacement result.

## New-game introduction

An installed package with nonblank `meta.introduction` shows its Markdown in a scrollable modal occupying 37.5% of viewport width and 75% of viewport height before a new game starts. Continue acknowledges it and initializes the authored world exactly once. The playable scene is not mounted before acknowledgment. While the introduction is pending, the session contains no initial items and writes no save, including during application close; elapsed reading time is drained before initial placement. Closing before Continue therefore shows the introduction again next time. A valid existing save bypasses it, and an absent or blank introduction preserves immediate startup. Hard reset removes the save and shows the introduction again. The Editor's live Board does not show this player introduction.

## Cheats, save, and presentation

Cheat availability is application preference; enabled cheat state, including Speed up, is Runtime state. A fresh Editor Board enables cheats with Default authored timing. Speed up uses the fixed shared `GameplaySpeedUpMultiplier`, passed by Game and Editor composition into the session and Tick. Tick requests one unchanged 100 ms simulation step at a wall-time cadence derived from the multiplier. Each accelerated wake publishes at most one step; when computation or the host falls behind, excess accelerated wall time is discarded rather than accumulated into catch-up bursts. The next wake accounts for computation time and always yields to the host. Thus the configured acceleration is a target under load, not a guarantee; normal-speed elapsed-time replay stays complete. Switching the option does not advance or settle gameplay by itself. The multiplier is not player-configurable; individual domain timers do not read the shared constant. Hard reset is renderer lifecycle: discard the exact Game without final save, clear its complete save set (Current, Manual, and all checkpoints), then acquire a fresh Game. It is not an authored item command.

Serializable State contains items with their optional inventory bindings, deliveries, jobs, queues, current space, optional previous space, and gameplay cheat state—not wall-clock timestamps, Tick observation cursors, transient events, or UI state. Hydration strictly validates the current shape and invariants. Matching-major compatibility is defined only by [`VERSION.md`](VERSION.md).

[`src/game-event`](src/game-event) owns strict transient facts projected from already-applied transition results. Event-only commits do not mutate Runtime. Transition subscribers observe current-plus-tail, while event subscribers discard that current replay. Slow presentation callbacks cannot delay Runtime, Tick, save, or another subscriber. A failing callback cannot roll back or stall its triggering commit or peer delivery; afterward, the existing fatal session fail-stop applies.

Presentation may trail canonical Runtime and may redirect, shorten, collapse, or skip choreography. It never determines readiness, validity, placement, queue/job state, Tick progress, save, or event publication; a new subscriber never receives old events merely because another surface is still animating them.

Do not add queue reordering, wall-clock job timestamps, reverse reservation history, partial outcome, passive-storage production, or gameplay truth reconstructed from UI/events without an explicit new product design.

Production jobs never dim item artwork. Timed jobs project production progress; instant jobs preserve the item’s lifetime indicator without flashing a production state.


Installed games keep Current, a separate Manual save, and independent 5-minute, 30-minute and 4-hour checkpoints. Current follows autosave and final save; explicit Game Menu Save writes only Manual. Checkpoint intervals use real elapsed time and persisted snapshot timestamps, unaffected by Speed up. Each missing checkpoint is initialized on the first successful Current save; only due checkpoints are replaced on later saves, including after restart or a long gap. These are refresh intervals, not exact historical ages.

Game Menu Load lists every slot, including unavailable ones, with the relative age of each available save. Loading validates the selected save against the installed game's compatibility and runtime rules before discarding the live session. It restores the pinned selected snapshot as Current without first saving the abandoned world or rotating checkpoints. Normal startup still uses Current, with no silent fallback. Editor Board sessions remain ephemeral.

In the installed game, F5 writes Manual and F9 loads Manual through the same menu command and restore lifecycle. Held-key repeats and overlapping save/load actions are ignored. Missing Manual is reported without leaving the current game.

Applying a board template publishes its committed space and template identity. Presentation reveals the visible board’s items in reading order using the ordinary space-entry animation. This visual sequence does not delay or replay engine work.
