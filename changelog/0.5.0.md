# Arkini 0.5.0

Arkini 0.5.0 establishes the first complete baseline for the offline economy game, its deterministic gameplay engine, and the integrated game Editor. Players get production, finite resources, scheduled automation, multiple spaces, deterministic item handling, and durable desktop saves. Authors get one capability-based Item model, a playable Board, portable JSON projects, Flow and Estimate analysis, linked Notes, canonical Arkpack builds, diagnostics, and MCP-assisted authoring.

This is a pre-stable release with a fresh external-data contract. Read the migration notes before relying on projects, saves, or Arkpacks created by earlier development builds.

## For players

### Production, queues, and automation

- Items with production lines expose explicit player-controlled work. Enqueueing records intent; required materials travel physically to the owner, and a job starts only after the material has settled into its input.
- A blocked request no longer freezes all later work for the same owner. The engine selects the earliest request that can make real progress while preserving accepted queue order, so runnable work may overtake a request waiting for materials, rules, units, or output capacity.
- `Ctrl + left click` fills the remaining capacity of the default production queue. A normal click runs the item's primary action or selected default line.
- Clearing pending work returns unused buffered and travelling materials through ordinary placement. Active work remains untouched, and the clear is rejected atomically if every returned item cannot be placed.
- Clock-enabled items can periodically enqueue their selected automatic line, expire after a finite lifetime, or combine both behaviors. Manual and automatic work share the same queue, jobs, material delivery, output limits, and deterministic engine rules.
- Manual and automatic lines are selected independently. Interactive Clock items remain usable by the player, while automatic-only items deny production controls but keep ordinary movement, merge, and removal behavior.
- Paused Clock rules pause both interval and lifetime timers. Existing work earns the current simulation step before a new pulse is admitted, and accepted jobs may finish after the owner's lifetime ends.

### Units, materials, and finite resources

- Any item can carry a finite number of units, representing uses, health, stock, or another consumable supply independently from stack quantity.
- Production can spend units from its owner or from a deterministic Board target. Queueing itself is free; units are spent only when the job actually starts.
- Merge rules can spend one unit from the source or target, enabling finite-use tools, receivers, deposits, and harvestable resources. Spending the last unit applies that item's ordinary depletion output.
- Items with a finite lifetime remain live while travelling, buffered, reserved, or committed to work. If required material expires, the job either continues with enough remaining input or aborts without producing output; reservations return, queued intent remains, and spent units are not refunded.
- Consumed material is destroyed only when work completes. Reserved material keeps its live identity and is returned through normal placement after the job.

### Actions, spaces, and Inventory

- Items may provide an immediate Space or Inventory action instead of production lines. Availability is controlled by ordinary rules and optional inputs; a failed activation consumes nothing.
- Space actions support doors, portals, elevators, and other one-way navigation between authored Board spaces. Costs, depletion, output, and navigation settle as one engine-owned transaction before the destination is presented.
- Inventory actions open the global Inventory but grant no special storage privilege. Inventory remains available without a physical opener.
- Dragging an item with `I` stores it when its authored scope and Inventory capacity allow it. Clicking an Inventory item exclusively releases its complete stack and runtime identity; it never runs that item's action or production.
- An `any`-scoped Inventory release tries the current Board first and Toolbar second. A failed release leaves the stored item unchanged.
- Every Board space retains its items, jobs, queues, deliveries, and timers while another space is visible.

### Board, item handling, and presentation

- Every Board cell, Inventory slot, and Toolbar slot has one occupant. Board interaction has one visible layer with no hidden co-located item.
- Board and Toolbar interactions share the same item commands: left click uses the primary action, `Ctrl + left click` fills a default queue, `Shift + left click` splits a Board stack, and right click opens Item Detail.
- Drag and drop, swaps, stack transfers, directional merges, and production deliveries use canonical engine identity and placement rules. Stale interactions or blocked destinations do not leave partial state behind.
- Board, Toolbar, and Inventory share a fitted camera. Wheel or pinch zoom remains anchored under the pointer, right drag pans after the Item Detail click threshold, and `0` resets the current canvas.
- Authored artwork scale is respected consistently on the Board, Editor Board, Inventory, and Toolbar while the full tile remains the interaction and occupancy area.
- Running production owners share a clear activity treatment, including completed jobs waiting for output placement. Presentation may lag or shorten choreography without delaying gameplay.
- Item Detail reports current work, input progress, accepted queue rows, outputs, units, timers, and the reasons an operation is unavailable.

### Desktop behavior

- Window modes provide Default, Bordered, and Fullscreen choices, with `F11`, `Alt + Enter`, native fullscreen, maximize, and unmaximize synchronized back to the saved preference.
- Cheat tools are an optional player feature under Game settings. Instant gameplay accelerates jobs, deliveries, and finite lifetimes through the same authoritative engine rather than a separate shortcut implementation.
- Native startup and the renderer stay on one stable surface until the complete splash is ready. An unrecoverable renderer bootstrap failure closes the application instead of leaving a frozen shell.
- The macOS application requires macOS 13 Ventura or newer.

## Gameplay engine

### World, locations, and item state

- The Runtime contains multiple isolated Board spaces plus global Inventory and optional Toolbar storage. Equal coordinates in different spaces never interact, but every space continues simulating.
- New-game placement applies exact Board, Inventory, and Toolbar entries in authored order against one candidate Runtime. The complete initial state and current space commit together or not at all.
- Inventory and Toolbar bridge spaces as passive storage. Jobs pause and queues stop dispatching there, while moved owners retain identity-bound state until they return to a Board.
- Storage permission and query reach are separate. `universe` may query every Board plus passive storage but is never a storage scope.
- Only compatible pure items stack. Inputs, jobs, queued requests, partial units, schedules, and other identity-bound state make an item effectively single-quantity; attaching state to a stack atomically isolates one item and places the remainder.

### Canonical actions and atomic transitions

- Every gameplay mutation resolves live facts, plans from one pinned Runtime, validates the complete candidate, and commits Runtime plus exact transient events once. Rejection, interruption, or failed placement publishes nothing.
- Movement, release, split, removal, production, output, merge, depletion, expiry, and navigation all use the same canonical identities, count limits, and placement operations.
- Immediate item actions are a strict alternative to production lines. Space and Inventory actions share rule and input admission; there is no separate renderer-owned action truth.
- A line may opt into one-hop check-ahead capacity. When that owner item is produced, the engine admits it only when at least one eligible marked follow-up line could eventually fit its output count limits, without creating a hidden reservation or future job.

### Production lines, queues, and delivery

- Every item owns zero or more lines and an optional queue size. Items without lines are passive unless they provide an immediate action.
- The default line selects the player's primary production action; it does not run automatically. A Clock line independently selects periodic admission.
- A queued request owns no time, material, unit, or output reservation. During each pass, the engine traverses global accepted intent and chooses the earliest actionable request for each idle Board owner; blocked probes are side-effect free and may be overtaken.
- Autofill sends useful material through persisted deliveries with fixed-step travel time. Material becomes available only when Tick settles it; Pixi geometry or animation never admits input or starts work.
- Job start re-resolves rules, non-material requirements, units, material, queue ownership, and capacity, then atomically owns inputs, spends units, isolates stateful stacks, reserves worst-case output, creates the job, and removes its request.
- Active jobs are non-preemptive. There is no player cancellation command, no manual queue reordering, and no production in passive storage.

### Tick, jobs, Clock, and expiry

- Simulation advances in deterministic 100 ms fixed steps. One long elapsed interval is equivalent to the same explicit step sequence, and work admitted during a boundary receives no retroactive time.
- Jobs persist only duration and remaining time, pause outside the Board, and complete in stable identity order.
- Clock scheduling supports an interval, a finite duration, or both. Missing duration means unlimited lifetime; missing interval creates a one-shot lifetime with no production pulses.
- Clock interval phase advances only on the Board, while finite lifetime follows the identity through Board, delivery, input, and job ownership. Inventory and Toolbar reject finite-lifetime items.
- A Clock pulse attempts its exact selected line and never silently substitutes another line. An unavailable selection or full queue consumes no hidden debt.
- Job completion tied with material or owner expiry wins first. Expiry, optional output, affected-job reconciliation, queue cleanup, input returns, and reservation returns are deterministic atomic operations.
- Failed expiry output placement preserves the exhausted owner and pending state for retry; it loses or duplicates neither items nor work.

### Units, completion, and outputs

- Units are a capability of the single Item model. Missing live remaining-unit state represents the fresh authored amount and stays pure until units are partially spent.
- Start aggregates every unit cost by exact runtime payer and spends each payer once. Full depletion may remove an eligible idle payer immediately, while an active owner can remain at zero until completion.
- Active jobs reserve the worst possible future quantity of every output against `maxCount`, including ranges, chance, repeated weighted rolls, alternative output sets, and deferred depletion output. Queued requests reserve nothing.
- Completion removes consumed roots, retains reservations, applies line and depletion output, releases buffered inputs, and relocates reserved instances in one fixed order. Any capacity, unit, placement, or return failure preserves the ready job for deterministic retry.
- Gameplay randomness derives from stable canonical identities and explicit algorithm versions, never wall time or Tick timing. An unchanged blocked retry therefore resolves the same rolls and placement order.

### Placement, stacking, and merge

- One placement policy validates live quantities and reservations, applies authored scope and Board strategy, fills compatible pure stacks, creates fresh identities in empty locations, and requires the complete requested quantity.
- Random placement chooses a fresh Board origin for every resolved quantity unit and applies stack-first, nearest-first placement against the evolving candidate.
- Directional merge rules belong to the source item, and reverse matching is never inferred. Source use, consumption or unit spending; target keep, removal, replacement or unit spending; optional output; and source return commit together.
- Replacing a finite-lifetime target creates the replacement with its own fresh schedule. Ordinary same-item stacking remains separate from merge.

### Persistence, events, and failure isolation

- Serializable State contains items, deliveries, jobs, queues, current space, and gameplay cheat state. It excludes wall-clock timestamps, Tick observation, transient events, animation, and UI state.
- Hydration strictly validates the complete current shape and gameplay invariants before a Runtime becomes playable.
- Events are transient facts projected from an already committed transition, never a second state store. Slow or failing presentation and diagnostic consumers cannot delay or roll back gameplay truth.
- The first fatal session failure stops new commands and Tick progress and preserves the latest committed Runtime for diagnostics. A failed candidate can never become a save or incident state.
- Hard reset discards the exact live Game and its verified save before creating a fresh session; it is an application lifecycle operation, not an authored item command.

## For game authors

### Integrated Editor workflow

- Create a project with an explicit package ID, reopen an empty project, import a validated Arkpack, or open a current portable project directory directly in place.
- Dedicated Project, Items, Assets, Board, Flow, MCP, Notes, and Build workspaces keep authoring, analysis, testing, and publication in one application.
- The Items catalog combines fuzzy search, draft and reachability status, optimistic Estimate metrics, ordering, artwork, and direct navigation. Large item, asset, and selector collections are virtualized and searches are debounced.
- Item Overview summarizes identity, artwork, actions, production, Clock, units, merges, connections, Estimate, linked Notes, and deletion before routing to focused forms.
- New items may be marked as Editor drafts. Draft status is filterable and visible in catalogs and MCP, but it does not exclude the item from gameplay, Board testing, validation, or Build.
- Item and asset deletion show exact usage before a safe or explicit forced deletion. Item deletion removes stale Note links without deleting the Notes themselves.
- `Cmd + S` on macOS and `Ctrl + S` on Windows and Linux use the active Editor form's existing Save action, including item, project, asset, Note, and project-dialog forms.
- Forms preserve unsaved work, lock admitted saves, report exact validation fields, and avoid stale asynchronous writes or navigation. Capability sections can be enabled or deliberately removed before Save.
- Ordinary JSON saves are incremental: they write only changed source data and keep PNG bodies out of the mounted project projection. Large projects therefore avoid rereading and rewriting every asset on routine edits.

### One capability-based Item model

- Every item uses the same schema and is assembled from optional capabilities rather than a fixed type such as Producer, Deposit, Blueprint, Temporary, Space, or Inventory.
- An item may be passive, own production lines, provide one immediate Space or Inventory action, carry finite units, define directional merges, run a Clock schedule, expire, or combine compatible capabilities.
- Production lines support material and unit inputs, consume or reserve ownership, rules, runtime adjustment, deterministic or random outputs, queue capacity, default and Clock selection, and optional one-hop check-ahead capacity.
- Clock authoring separates periodic interval from finite lifetime and exposes expiry output only when a lifetime exists. Authors can choose interactive or automatic-only control.
- Actions and nonempty production lines are mutually exclusive. The Editor switches capabilities explicitly; JSON and MCP reject conflicting data instead of silently dropping fields.
- Every item requires an artwork scale from `0.25` through `1`; new drafts start at full scale. The Artwork form previews the complete default composition against the unchanged full tile.
- Item artwork currently uses the authored default composition and scale. Progress-based artwork selection is not part of this release.
- Initial Board and Toolbar entries define exact stacks at exact positions, while Inventory entries may also define an exact slot. Aggregate start quantities respect each item's global `maxCount`.
- Validation reports finite-unit items that have no deterministic authored recreation route as non-blocking design warnings.

### Canonical portable project

- The Editor and `arkini-cli game pack` consume the same directly versionable project directory; there is no second simplified or legacy authoring format.
- `project.json` owns writer provenance and the current authoring revision. `game.json` owns package metadata, structured output version, resources, layouts, and start state.
- Each `items/<uid>.json` contains one strict Item document. The path owns immutable UID; the item owns its editable human-readable gameplay ID. Renaming an ID rewrites exact references while preserving UID.
- `assets/*.png` contains item artwork, `resources/*.png` contains package-shell imagery, and `notes/<noteId>.json` contains portable authoring Notes. Locks, temporary files, and ignored build output are not game source.
- Generated `schema.json` plus explicit `$schema` links make project and Item files inspectable by external JSON Schema tooling.
- JSON export creates a new uniquely named child, copies only portable allowlisted paths, validates the completed result, preserves source Git metadata and unrelated files, and never overwrites an existing destination.

### Build, output version, and installation

- Authors choose Arkpack output `major`, `minor`, and optional suffix directly in Build. Build saves valid version settings before compilation and retains them even if compilation fails, without advancing the authoring revision or resetting the live Board.
- Compatibility is an author decision. There is no internal project VCS, automatic semantic bump, committed HEAD, snapshot object store, or content-diff version classification.
- Editor Build and the CLI compile the current saved source tree directly, using the same strict reader, validator, compiler, artwork normalization, MessagePack encoding, gzip packaging, and publication path.
- Item artwork is normalized to aspect-preserving RGBA PNG no larger than 256 x 256 without enlarging smaller sources. Package-shell resources preserve their exact source bytes and dimensions.
- Build results survive workspace navigation. The artifact records its exact output version, source revision, content hash, size, and diagnostics; authored-content changes mark it stale.
- `Save as...` publishes one self-contained Arkpack. Install and Update revalidate it immediately before atomic catalog replacement and do not silently delete an existing save.
- Local and Editor builds are playable Community Arkpacks. Tagged release automation may embed keyless Sigstore proof and publishes the same signed Arkpack bytes in every native package.
- Repository builds and previews cache an unchanged official Arkpack using a canonical source fingerprint plus artifact checksum. Direct CLI packing, Editor Build, and signed releases still perform their normal canonical build behavior.

### Playable Board, Flow, and Estimate

- The Editor Board runs the real engine, Board, Toolbar, Inventory, Item Detail, audio, rendering, and commands used by the packaged game.
- The live Board is ephemeral and never autosaves into the project. Refresh or project replacement discards it; Arkini does not maintain named Board scenarios.
- Authors can switch directly to any configured space and use Default or Instant gameplay while testing.
- Flow maps authored acquisition and consumption relationships in either direction, with configurable depth, root focus, deterministic layout, and links back to owning forms.
- Estimate performs optimistic static authored-dependency analysis: parallel critical-path duration, expected random-output economics, materials, owners, infrastructure, units, Clock lifetimes, and positive prerequisites.
- Estimate metrics are available in the Items and Assets catalogs as well as per-item detail. Unreachable items and unused assets are called out directly.
- Flow and Estimate are design tools, not runtime simulation. They intentionally do not reproduce concrete placement, live identity packing, all rule interactions, or engine scheduling.

### Linked Notes and Assets

- Portable Markdown Notes may link to any combination of Items and Assets. Project Notes and filtered Notes tabs on Item and Asset detail share the same authoring model.
- Item relationships use immutable UIDs; asset relationships use canonical resource IDs. Item deletion strips missing links, while resource rename or deletion rewrites links atomically without discarding unrelated relationships or Note content.
- Notes use freshness timestamps to reject stale writers, do not advance project revision, and never enter Build or Arkpack output.
- Assets support import from PNG files or another Arkpack, usage inspection, direct Item creation, safe rename/delete, and lossless Optimize for item and package imagery.
- Asset grids identify usage and related Estimate state. Stable card sizing, full previews, transient copy feedback, and hover zoom keep large catalogs readable.

## AI-assisted authoring

### Editor MCP

- Start a local project-scoped MCP endpoint from the Editor, or run a selected project's saved endpoint headlessly through `arkini-cli editor mcp <projectId>`. An OAuth-protected ngrok endpoint is available explicitly for remote use.
- MCP reads project configuration, validation, item and asset catalogs, complete item configuration, relationships, Notes, individual estimates, and the global Estimate index.
- `create_item` and `edit_item` author the same single capability-based Item schema as the Editor. Stable schema IDs and `schema_detail` expose every strict structured contract to an LLM before mutation.
- Focused tools update project configuration and layouts, manage exact start items, rename IDs with references, inspect deletion impact, and safely delete Items.
- Note tools search, read, create, edit, and delete Markdown content together with complete Item and Asset relationship arrays using freshness checks.
- Every MCP mutation uses the canonical project repository and revision checks; it never maintains a second project copy. Running the GUI Editor and headless MCP against the same project concurrently is unsupported.

## Arkpacks, saves, diagnostics, and delivery

### Artifacts and compatibility

- A package has one identity: `game.json` `meta.id`. Catalog paths, manifests, filenames, saves, and runtime state derive or verify it instead of copying a competing identity.
- Arkpacks are self-contained data-only artifacts containing strict gameplay configuration and supported PNG resources; they never contain executable JavaScript or HTML.
- Official provenance comes from offline verification of the embedded Sigstore proof over the immutable gameplay payload and configured release channel. Missing or invalid proof produces playable Community content, not a load rejection.
- Save files use the compact versioned envelope `{ version, arkini, state }`, remain separate from packages, and are written atomically.
- Arkini-owned application data admits matching release majors only; minor and patch versions never select a parser or migration. Project-owned output versions use `major.minor[-suffix]`, and only the gameplay major controls save compatibility.
- Invalid package data never exposes save deletion. Recovery is offered only after a verified package fails during save decoding or Runtime hydration.

### Diagnostics and CLI

- The installed macOS CLI supports schema generation, validation, canonical packing, Arkpack verification, project listing, headless Editor MCP, exact gameplay replay, and diagnostic slicing.
- A fatal installed-game session best-effort replaces one local incident with the exact Arkpack and latest committed save plus linked human-readable failure, history, and Runtime reports.
- `arkini-cli game replay` runs an incident or explicit Arkpack/save pair through the production Game Session without touching installed saves and distinguishes a reproduced fatal failure from a bounded timeout.
- `arkini-cli diagnostics slice` extracts a focused summary, failure, history, or Runtime section from the latest incident or rotating gameplay diagnostics for human or LLM inspection.
- Rotating application diagnostics record bounded main-process, renderer, and Editor failures with severity, application version, platform, architecture, and visible truncation markers.
- Production packages intentionally omit source maps; exact replay, incident reports, application logs, and diagnostic slicing are the supported debugging surface.

### Native delivery

- Release tags publish unsigned macOS Apple Silicon DMG and ZIP, Windows x64 installer and ZIP, and Linux x64 and arm64 AppImage packages with SHA-256 checksums.
- Every native package embeds the exact same once-signed Official Arkpack bytes, also published as a standalone artifact.
- Hosted development-branch validation runs the complete repository gate on Linux and focused filesystem, Electron, Arkpack, source, and schema-writer portability gates on macOS and Windows.

## Reliability

- Project, export, build, Arkpack proof, save, JSON Schema, Note, OAuth, and diagnostic data have strict ownership and validation boundaries.
- Recoverable filesystem transactions serialize competing writers, validate exact paths and revisions, recover interrupted replacements, and preserve the previous committed state on failure.
- External project operations modify only Arkini-owned paths and preserve `.git` plus unrelated files.
- Editor project state holds resource metadata rather than PNG bodies. Requested previews use bounded versioned caching, while Build rereads and verifies the exact saved bytes it publishes.
- Drafts and pending saves remain bound to their exact form and project revision. Stale async results cannot redirect, overwrite, or dismiss a newer authoring session.
- Game truth commits independently from rendering, animation, audio, persistence, diagnostics, and React lifecycle; failures in those consumers cannot create a competing Runtime.

## Authoring and migration notes

- Arkini 0.5.0 is pre-stable. Matching application majors pass version admission, but obsolete development shapes may still fail strict current-shape validation.
- No automatic migration, legacy reader, or conditional compatibility path is provided for unsupported pre-0.5.0 projects, Arkpacks, saves, scenarios, internal Version history, or other persisted Arkini data.
- The Editor accepts only the portable project rooted by `project.json`; earlier IndexedDB, SQLite, arbitrary-fragment, typed-item-directory, scenario, and internal Version layouts are not imported automatically.
- All item records must use the single Item schema at `items/<uid>.json`. Fixed item-type discriminators and nested `items/<type>/` paths were removed.
- Charges were renamed and generalized to Units. Temporary lifetime and scheduled production now share the optional Clock capability; Deposit, Blueprint, Producer, Craft, Stash, Space, Inventory, Temporary, Clock, Simple, and Common are no longer separate Item types.
- Board ground/content layers and progress-based artwork selection are not part of the current contract. Each Board cell has one occupant, and runtime artwork uses the default composition at its authored scale.
- Named Editor Board scenarios and Arkini-managed project history were removed. Use Git for project history and choose Arkpack output version explicitly in Build.
- The embedded Editor ChatGPT workspace was removed. AI-assisted authoring remains available through the project-scoped MCP server.
- Item categories and tags were removed. Selectors and relationships use exact Item references; every Item retains a globally unique immutable UID alongside its editable authored ID.
- Older source projects must be recreated or deliberately converted to the current schema and packed again.
- The durable no-data-break guarantee begins only after the product owner explicitly declares the first stable baseline; it does not apply retroactively to obsolete pre-stable data.
