# Arkini agent contract

Arkini is an offline, data-driven economy game and Editor. Work as a senior engineer and architect: prefer the smallest explicit design, keep ownership visible, and optimize code and documentation for future LLM comprehension. Engine code is the reference style.

## Operating rules

- Questions and analysis requests are read-only. Edit only on explicit implementation intent.
- Use current source and tests as evidence. Active contracts are [`README.md`](README.md), [`ARCHITECTURE.md`](ARCHITECTURE.md), [`GAME.MD`](GAME.MD), [`CONFIG.md`](CONFIG.md), and [`VERSION.md`](VERSION.md); GitHub Issues own backlog. History is not current authority.
- If code and an active contract disagree, stop and resolve the contradiction in the same change.
- Repository commands live only in [`Argcfile.sh`](Argcfile.sh). Run them through local `argc` (`argc typecheck`, `argc test [paths...]`, `argc check`); never infer npm scripts from history.
- Follow [`VERSION.md`](VERSION.md): readers gate on major only. Until the owner declares a stable baseline, add no migrations, legacy readers, obsolete-shape fixtures, or minor/patch-conditional paths unless explicitly requested.
- Accessibility is not an Arkini concern. Do not add or preserve ARIA, screen-reader semantics, accessibility-only focus presentation, keyboard-only paths, tests, or review. Pointer, keyboard, and focus behavior is valid only when it is deliberate product UX, never for accessibility compliance.
- Gameplay motion is intentional; do not add reduced-motion branches.
- Comments explain ownership, invariants, temporal boundaries, or why a simpler-looking design is wrong. Do not narrate syntax or preserve dead history.

## Architecture defaults

- One canonical runtime truth; React, Pixi, events, caches, and persistence never become mirrors.
- Domain-first ownership; no generic junk drawers or speculative frameworks. Root `shared/` is limited to immutable cross-process build metadata/limits, never domain behavior.
- Production modules default to `src/<domain>/<type>/<file>`, where `<type>` names the code grammar (`fn`, `fx`, `ui`, `schema`, `error`, `service`, `layer`, `atom`, or another equally exact kind). A deeper directory is a finer ownership boundary, not filing convenience: justify that independent policy, lifecycle, or capability in the owning contract. Repeated or deep nesting is evidence that the domain itself is too broad.
- Domain ownership names meaning and dependency direction; it is not access control. Any owner may directly import a well-designed component, pure operation, schema, type, or capability when its contract fits and the dependency points the right way. Prefer that exact reuse over duplication, forwarding APIs, adapters, or wrappers introduced only because the implementation lives in another domain. Split a broad owner into shallow semantic roots when that makes independently useful contracts visible.
- Engine decisions stay in engine/domain operations. UI binds controls and renders projections.
- Use Effect where it clarifies operations, dependencies, concurrency, or lifecycle. Follow the mandatory grammar below.
- Prefer a linear concrete flow over adapters, registries, synchronization, and forwarding introduced for hypothetical reuse.

## Code grammar

- A total synchronous value operation depending only on explicit arguments and immutable module constants is named `fooFn`, including when it is a private helper inside its exact owner's module. It is observationally pure: it returns neither Effect nor Promise, does not throw, and does not use `Effect.run*`, ambient or global state, clock, randomness, I/O, subscriptions, schedulers, live or shared mutation, or stateful capabilities. Call-local mutation of fresh scratch or output values allocated during that invocation is a valid computation detail; that state may pass through private helpers but is never retained for later work. A `*Fn` never mutates an argument or anything reachable from an argument, and a completed fresh value may escape only as the returned output with no retained alias. Diagnostics, `Option`, and discriminated results may remain data.
- Primitive `*Fn` helpers are private and co-located with their exact owner by default. Prefer one cohesive linear owner over a constellation of tiny exported modules and import hops; file length alone is not a split rule. A standalone exported `fooFn.ts` is justified for an independently useful policy, algorithm, or calculation with a clear public contract; it need not remain private merely because its first consumer lives in the same domain. Put a distinct responsibility in its own shallow semantic domain when that exposes a cleaner reusable contract than a broad owner. Callers import the exact operation directly—never add a forwarding API, adapter, or duplicate solely to preserve artificial domain privacy. `fn/` contains only total explicit-input data-to-data operations and their operation-owned declarations, never Effect programs, schemas, standalone types, Context/Layer/error/capability declarations, constants, or a global/shared junk drawer.
- An Effect operation is named `fooFx` in `fooFx.ts` when it owns typed failure, environment, time or randomness, I/O, async work, interruption, concurrency, scope or resources, live mutation, subscriptions, transactions, or stateful capabilities. `Effect<_, never, never>` is a review trigger, never an automatic conversion rule.
- Every production Arkini-owned named callable value makes its execution representation explicit. A callable Props/Output/capability field, function-valued parameter, destructured binding, or local callback ends in `Fn` when invocation returns an ordinary JavaScript value, `void`, `Promise`, or `PromiseLike`, and in `Fx` when invocation returns `Effect`. For callable values, `Fn` identifies direct JavaScript invocation and does not assert that an imperative callback is observationally pure. The stricter totality and purity guarantee above applies when the identifier declares a project value operation. React components and `use*` hooks retain framework grammar. JSX/DOM and external-library property or method names keep their prescribed spelling; suffix the Arkini-owned value passed to them. Anonymous inline callbacks have no suffix.
- Composition is one-way: Fn may call Fn; Fx may call Fn or Fx; Fn never calls or runs Fx.
- Framework declarations keep framework grammar: React components and `use*` hooks, Effect Atom declarations, Zod schemas, Effect Context/Layer/error declarations, types, namespaces, constants, and inline callbacks are not project operations. Existing plain-operation violations are cleanup debt, not precedent or a reason to widen unrelated work.
- Prefer one cohesive public ownership boundary per file. Sole-owner helpers, commands, constants, Props, Result, and other implementation declarations stay private and co-located with that owner. Split when a policy, lifecycle, capability, component, or contract is independently meaningful or reusable; do not export implementation details merely to keep files short or directly test them. Once such a contract is public, consumers may use it directly across domains subject to the real import direction. Public and cross-module domain contracts use their concrete owner type rather than `ReturnType`, `Effect.Success`, `Layer.Success`, or a 1:1 proxy alias. A framework-generated configured API with no stable public extractor stays inferred at its exact owner instead of manually mirroring unstable library generics. Standalone public schemas, typed failures, Context/Layer/capability identities, Atom state identities, and framework entrypoints retain their own domain-owned files. Do not create catch-all barrels or `types.ts` piles.
- Reusable Arkini capabilities are readonly objects produced by explicit Effect factories. Do not add project-owned classes, constructor-injected repositories, managers, generic services, or adapters. Framework/external constructors remain valid.
- All exact identifiers use the shared `IdSchema`. Business schemas are strict unless unknown keys are deliberate and export `FooSchema`, `type FooSchema = typeof FooSchema`, and `namespace FooSchema { type Type = z.infer<FooSchema> }`.
- Effect services/Layers own real capabilities and lifecycles, not ordinary domain logic. Scoped fibers/resources belong to a Scope; production time/randomness use injected Effect services.
- Orchestrators read in domain order (`resolve → assert → plan → apply`) and own sequencing/transaction boundaries. Do not hide that order in generic pipelines or mutable mini state machines.
- Expected rejection is typed failure. Defects remain defects unless isolated at the correct external boundary; preserve observable error precedence.
- UI may consume UI and non-UI owners; non-UI code never imports a `ui/` module. UI consumes semantic tokens and shared primitives (`src/ui/ui`) instead of page-local copies. Use exhaustive matching for real state variants, focused ownership hooks for non-trivial lifecycle, and a stable `data-ui` marker on substantial DOM owners; Pixi does not create a DOM/ARIA gameplay mirror.
- Prefer native HTML state when it directly owns product behavior. Otherwise project semantic visual state through `readDataUiFn` into typed `data-ui-*` attributes and style stable selectors; never encode application state in ARIA or duplicate the same decision through conditional `className`, `cn`, or `twMerge` branches.
- React components may and should compose cohesive screens from smaller components. Extract a component for independently meaningful presentation or interaction ownership, actual reuse across Game, Editor, Launcher, and other products, or a real render boundary; keep private single-owner presentation helpers beside their public component. Before duplicating a similar surface, compare its semantics and prefer one cross-product `src/ui` component with explicit composition, slot, or variant inputs when behavior and ownership are genuinely shared. Do not abstract incidental CSS resemblance, speculate about future reuse, split by line count, or replace one readable component with forwarding wrappers.
- A meaningful stateful surface may use a neighboring typed `useFooController` when it provides one coherent, nameable responsibility. The hook exposes `useFooController.Props` and `useFooController.Output`; component props extend the controller input (`interface FooProps extends useFooController.Props`) and add only presentation or composition inputs. The controller owns the state, effects, lifecycle, asynchronous command orchestration, and semantic callbacks for that one concern; the component owns JSX, attributes, simple presentation decisions, and straightforward DOM/event binding. A controller may retain a DOM ref or event adapter only when that resource lifecycle is its responsibility. It may compose smaller focused hooks when it adds meaningful coordination and an explicit public contract; pass inputs and project outputs by name, never merge hook result bags with object spread. Compose focused hooks or child components directly when concerns are independent; never create a god-controller that merely relocates a god-component, mirror the component through hook input/output, or let controller state replace domain, Atom, Effect, repository, or other canonical truth. Small stateless leaves need no controller.
- Stabilize hook callbacks and composite values when their identity crosses a memoized child, React effect or subscription dependency, Context provider, ref adapter, or another identity-sensitive boundary. Do not add `useCallback` or `useMemo` to handlers used only by native DOM elements, or when semantic inputs necessarily change the value on each render.
- Enforce stable import directions and graph integrity with Dependency Cruiser, semantic ownership with the active contracts and review, types/schemas with TypeScript/Zod, and behavior with focused tests. Never add source-text or custom-AST policy tests for names, calls, copy, token spelling, or topology.

## Tests

Tests are fast risk feedback, not a coverage project.

- All tests and test-only support live under the top-level `test/` tree beside `src/`, never inside `src/`. Mirror the production domain/type path where it makes ownership easier to locate; do not invent deeper test-only topology for a single fixture.
- Every test protects one named Arkini regression: a high-risk behavior, invariant, failure boundary, or lifecycle contract. If that regression cannot be stated, do not add the test.
- Test the authoritative lower layer. A higher-layer test must prove a distinct boundary risk such as admission, exact identity wiring, cancellation, stale-result suppression, destructive navigation, or settlement—not repeat engine/schema/selector facts through React DOM.
- Prioritize engine transactions, Tick, jobs, output, placement, merge ownership, persistence, compiler, and Arkpack integrity/trust/load/signing; then renderer-process concurrency; UI presentation last.
- Do not test copy, CSS/token spelling, markup inventories, visual tuning, framework behavior, trivial passthroughs, schema mechanics, enum membership, defaults, or permutations without distinct risk.
- Use the smallest representative synthetic fixture. Permanent tests must not depend on `game/arkini`, generated official snapshots, or platform packaging.
- Keep scenarios readable. Around 250 lines is a review signal; move non-trivial fixtures beside `Foo.test.ts` under `Foo.test/`, without a global fixture DSL.
- Search the owning suites first. Do not duplicate an existing proof; delete an older scenario when a new one subsumes it.
- Test private `*Fn` helpers through their owner's public behavior. Extract and test a standalone pure operation only when it owns an independent contract rather than to make an implementation detail importable.
- Run the narrowest useful focused suite while implementing. `argc check`, build, hosted/platform delivery, and packaging are deliberate closing gates, not substitutes for focused feedback.
- Hosted branch and prerelease validation runs the complete `argc check` once on Linux. macOS and Windows run `argc platform-check`: the production build and Community Arkpack verification plus the real filesystem, Electron, pack, source, and schema-writer suites. Pure engine, domain, and UI behavior is not repeated per operating system.
- A regression that depends on native filesystem semantics, paths, Electron-main integration, or portable artifact I/O belongs under an owner already selected by `platform-check`; extend that canonical command in the same change when a new platform boundary has a different owner. `platform-check` is hosted portability evidence, not a local substitute for focused tests or the complete closing gate.

## Independent review

For substantial work, use read-only agents when useful:

- **Reviewer:** checks the touched boundary against this contract and its owning domain document.
- **Clean head:** explains the resulting design from minimal context and flags hidden mental load.
- **Code bloat:** looks for avoidable files, machinery, duplication, and oversized diffs.
- **Worker:** implements one bounded, explicitly owned slice.

Run at least one standalone read-only reviewer for substantial code or architecture changes. An implementation worker does not approve its own work. Reviews may validly conclude that no further change is needed.

A review is read-only unless implementation or external tracking is explicitly requested. Record `.git`, HEAD/baseline/range, dirty state, and toolchain; review the diff plus complete touched ownership boundaries. Each finding states contract, exact location, actual behavior, impact, evidence type, required behavior, and focused proof. Distinguish reproduced, generated-output observation, deterministic test, direct structural inference, and speculation (not a finding). P1 means release/security/data/canonical-truth/core-lifecycle blocker; P2 means material recoverable contract or maintenance defect. Ignore taste and hypothetical extensibility.

Validate focused → affected → broad as risk requires, using `argc`; report hangs, failures, skipped platforms, and generated/package smoke honestly. Preserve unrelated worktree changes and remove probes. If issue tracking is requested, search open/closed Issues before creating or duplicating anything.

## Product boundaries

The Game loads an Arkpack and runs the canonical gameplay engine. The Editor authors portable projects and provides Item editing, Assets, Board scenarios, Flow, Estimate, Versions, Notes, Build, and a project-scoped MCP server. Flow is the authored relation graph; Estimate is optimistic static authored-dependency analysis using bounded output distributions, expected first-hitting time, deterministic complete-route choice, shared finite roots and co-products, and parallel critical-path timing, not runtime simulation.
